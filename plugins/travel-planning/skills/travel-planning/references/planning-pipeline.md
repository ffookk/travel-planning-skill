# 标准规划流水线

整条流程分为“公共库复用 → 采集 → 编排 → 审查 → 稳定候选晋升 → 交付”。阶段之间通过文件和门槛连接，不在采集过程中边查边写最终页面。新增数据源或 Agent 时，只要遵守输入、输出和字段所有权即可接入。

## 0. 公共库复用、建档与路线确认

主 Agent 先搜索 `.travel-library`，将确定采用的稳定实体 revision 固化到单次旅行的 `state/library-seed.json`；再创建 workspace，保存 `brief.json`、路线候选和用户确认后的 `selected-route.json`。公共库只提供稳定基线，日期、价格、开放、库存、天气和临时公告仍需本次重新查询。路线确认前只做足以比较城市顺序、交通大类、节奏和预算区间的轻量研究，不启动逐景点、逐餐厅深挖。

阶段输出：

- `brief.json`
- `route-proposals.json`
- `selected-route.json`
- `state/library-seed.json`
- 日期、人数、住宿夜、预算状态、硬约束和偏好的稳定版本

门槛：日期、出发地、人数和路线方向已确定；任何变化都要更新输入版本并使旧任务结果失效。

## 1. 前置数据采集

主 Agent 先运行数据源预检：所有 MCP 完成 `initialize`、`tools/list` 和只读上游 smoke query，天气完成真实 API 请求，小红书完成安装与登录态检查；再创建 assignment 并并行派发研究任务。本次路线必需的数据源通过 `--require` 声明，失败时预检返回非零，必须修复或明确切换到合规 fallback 后再派发依赖任务。assignment 固化公共库 seed、领域结果模板及其摘要；Agent 只产出本次实体、公共库候选、事件补丁、约束和未解决项，不写完整行程，不写长篇调研报告。

### 第一波并行

| 任务 | 主要工具/来源 | 必须落盘的数据 |
| --- | --- | --- |
| `attractions` | 景区官方、文旅公告、地图 POI、小红书近期体验 | 景点实体、运营时间、官网/预约/公告入口、入口/出口、内部节点时间轴、讲解、许可图片、内部交通、票种和预约动作 |
| `route-data` | 飞猪 FlyAI 多排序覆盖、飞常准 Aviation/Tripmatch、12306 最终复核、航司/客运方、高德、包车/租车平台 | 酒旅快照 ID、绑定具体 offer 的城际方案、交通边、门到门耗时、费用、行李、备选和复核入口 |
| `stay-food` | 飞猪 FlyAI、酒店官方页、平台手动会话、地图 | 酒旅快照 ID、绑定具体 offer 的住宿候选、可停车入口、行李条件，以及根据路线骨架提出的用餐时间窗 |

任一槽位释放后启动 `weather-risk`，读取日期、地点和已知活动类型，输出带固定图标代码、查询入口和复核时间的天气对象，并将影响绑定到具体事件或 checkpoint。天气尚未进入可靠预报窗口时，不虚构精确预报。

### 第二波补全

景点入口/出口、住宿锚点和用餐时间窗提交后，依次创建三个带显式 stage 的任务：`restaurant-discovery` 输出每个正餐的 2～3 个实体候选、动态平台信号、近期社区共识和图片/相册来源；`route-data-meals` 为每餐生成唯一基准路线，再为每个候选补齐“上一锚点 → 餐厅 → 下一锚点”及额外绕行；`restaurant-ranking` 同时读取前两项结果且只输出最终排序和主备切换条件。三阶段候选集合必须完全一致，空 `complete` 会被拒绝。它们分别落盘且禁止覆盖，同时补齐：

- 酒店/车站 → 当日首景点入口
- 相邻景点出口 → 下一景点入口
- 末景点出口 → 酒店/餐厅/车站
- 每个餐厅候选的两段精确路线、停车/步行和绕行数据

后续 assignment 只有在依赖结果完整提交后才能创建，依赖文件纳入输入版本摘要。不能在路线距离未知时把网红店直接选为主选。

行前就绪任务读取城际方案，补充节假日、临时公告、行李、证件、通信、保险和分阶段复核；不适用项显式写明。

### 采集门槛

- 每个拟采用景点都有可定位入口和出口、开放/停入、基础票、必选景交、可选项目、内部卡点和预约结论。
- 每条移动都有稳定 `route_id`，中国境内地面路线有坐标、高德数据和独立跳转链接。
- 每个完整旅行日都有与路线相符的正餐时间窗；正常正餐有 2～3 个餐厅候选、主选/备选、动态快照、可视证据和双腿路线评估；午餐/晚餐不能藏在交通或休息事件的描述里。
- 动态价格、余票、库存和运行状态先落 `snapshots/<task_id>/`；候选通过 `inventory_refs[]` 绑定具体 `snapshot_id + offer_id`，并保留过期时间和复核入口。
- 开放式航班/铁路发现已覆盖最早、最晚、时长、价格和推荐排序；单次低价或推荐榜不能作为全天无合适班次的证据。
- 住宿候选保存人数、房间数、床型和连续入住夜；酒店身份已按全名、城市/行政区、地址和坐标核验。供应商未返回多间同房型库存时只标记报价候选，不写成有房。
- 所有结果都已提交到 `results/`，所有快照、来源和允许留存的证据都在 `snapshots/`、`sources/`、`evidence/`，不只存在于 Agent 上下文。

## 2. 主 Agent 编排与汇总

本阶段默认不重新浏览网页。主 Agent先校验任务结果和来源，再按稳定 ID 合并；只有发现明确缺口时才创建 `gap-*` 修补任务，不把补查混入最终写作。

合并顺序：

1. 建立景点、交通、住宿、餐厅和用餐时段的 canonical entity registry。
2. 将各任务 `source_snapshot_ids[]` 指向的不可变快照汇入 `planning.source_snapshots[]`，再锁定预约场次、航班/车次、停止入场、日出日落和末班交通等硬时间。
3. 为每个景点生成稳定事件 ID，写入结构化开放/预约信息，并把入口到出口的节点排成带时间、讲解、图片、内部交通和补给的嵌套时间轴。
4. 在相邻事件间插入交通边，并核对门到门时间与缓冲。完成硬时间候选事件流后立即做一次可行性预审；景点/餐窗重叠、接驳不足、晚间活动晚于末班车或入住衔接失败时，先重排并按“换交通方式、缩短次要景点、取消次要活动”降级，再继续餐厅排序和页面编排。
5. 把正餐作为一等事件插入可执行窗口，合并餐厅实体、动态快照和路线评估，明确主选、备选、平台信号、特色、图片、前后距离、绕行与切换条件。
6. 插入住宿、入住退房、行李寄存/随车和休息事件。
7. 将天气、费用和预约任务通过带 `target` 与 `operation` 的事件绑定注入对应事件、景点卡点或交通边；不再依赖自由文本里的 `subject_id`。
8. 将每次字段冲突的采用值、理由和来源写入 `state/merge-decisions.json`。
9. 生成 `artifacts/itinerary.json`，预算只能由事件费用派生。
10. 确定性审查和事实审查均通过后，主 Agent逐个审核 `state/catalog-candidates.json`，将真正稳定的候选以版本锁晋升到公共库；动态事实不晋升。

编排阶段只保留会改变行动的文字。下列内容不进入事件卡：目的地百科、重复的路线优点、泛泛的“注意安全”、研究过程、无法改变决定的来源说明。每一行可见文字都应回答何时、去哪、怎么走、做什么、吃什么、花多少、何时抢或失败后怎么办。

## 3. 独立审查

最终审查读取合并后的 `itinerary.json`，不继承研究 Agent 的结论作为默认正确答案。审查结果写入独立文件，由主 Agent 修复后重新运行，直至没有阻断项。

审查分四类：

1. 数据完整性：ID、引用、来源、查询时间、动态状态、酒旅 snapshot/offer 绑定、门票分项、餐厅候选/快照/图片/路线和预约动作是否齐全。
2. 时间与空间：时间是否重叠；停止入场、最晚离开、用餐、入住退房、行李和交通缓冲是否可行；相邻地点是否有路线。
3. 事实与风险：官方事实是否被社区内容覆盖；余票、价格和天气是否被误写成未来承诺；高风险结论是否再次核验。
4. 页面可执行性：卡片是否直接展示必达点、内部顺序、抢票时间、费用、餐饮和地图；是否仍有汇报式空话、重复区块或不可点击的查询入口。

审查输出：

```json
{
  "status": "pass",
  "blocking": [],
  "warnings": [],
  "restaurant_audit": {
    "meal_slot_count": 3,
    "used_meal_slot_count": 3,
    "restaurant_count": 7,
    "snapshot_count": 7,
    "route_evaluation_count": 7
  },
  "inventory_audit": {
    "snapshot_count": 3,
    "selected_reference_count": 2,
    "expired_snapshot_ids": []
  },
  "checked_event_ids": [],
  "checked_at": "2026-09-20T18:00:00+08:00"
}
```

只有 `blocking=[]` 才能渲染最终 HTML。警告必须是无法在当前阶段消除的动态复核事项，并附时间和入口。

## 4. 渲染与交付

运行渲染器后检查手机和桌面视图、地图预览与全屏、外部链接、图片失败降级和打印版。最终交付 `itinerary.json`、`itinerary.html`、审查结果和少量必须由用户处理的预约动作。

## 扩展接口

新增 Agent 或数据源不得直接改 `itinerary.json`。它应声明：

- 读取哪些 `input_paths` 和 `dependency_paths`
- 拥有哪些 `owned_paths`
- 产出哪些 `entities`、`event_bindings`、`constraints` 和 `source_ids`
- 哪些字段由它负责，哪些字段只可引用
- 完成门槛、失败状态和复核时效

例如新增“演出活动 Agent”时，只需产出演出实体、场次硬约束和景点事件补丁；主 Agent仍按相同合并与审查流程处理，无需改变其他 Agent 的职责。
