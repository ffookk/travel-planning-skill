# 餐厅候选研究与路线适配

餐饮是路线确认后的前置研究。先稳定景点出入口、住宿锚点和交通骨架，再建立餐窗、发现餐厅、计算绕行并排序；未完成本流程的正餐不能进入 `confirmed_planning`。

## 三阶段流水线

1. 主 Agent 根据事件骨架生成 `meal_slots[]`，固化日期、餐别、时间窗、前后锚点、交通方式、最长绕行、用餐时长、预算、饮食和停车约束。
2. `restaurant-discovery` 搜索餐厅身份、平台信号、近期社区体验与合法可视证据，输出 `meal_candidate_sets[]`。正常每餐提交 3 个、最低 2 个候选，不提前排名。
3. `route-data-meals` 为每餐生成唯一 `meal_baseline_routes[]`，再为所有候选计算“上一锚点 → 餐厅 → 下一锚点”的同口径路线和额外绕行。
4. `restaurant-ranking` 同时读取 discovery 与路线结果，只从候选集合中生成最终 `meal_options[]`、主备排序和切换条件。
5. 审查检查候选数量、身份、来源、距离、评分语义、图片权利和动态状态，阻断项清零后才能渲染。

三个任务使用不同 `task_id`，结果不可覆盖。后续任务只在依赖以 `complete` 提交后创建，依赖内容进入 `input_revision`；三阶段候选集合必须一致。

机场安检区、封闭景区、服务区或深夜到达地等确实不足两个商户时，可使用 `candidate_policy.status=constrained`，但要记录搜索范围、唯一候选证据、应急补给和复核时间。

## 数据分层

### 餐厅实体

`planning.restaurants[]` 只保存慢变化身份：规范名称、别名、菜系、地址、坐标系、地图 POI、电话、长期特色菜、饮食标签、固定入口和许可图片。结构遵守 `schemas/restaurant.schema.json`。

地址必须定位到具体经营点，不能使用“景区附近”“酒店周边”或 `unknown`。中国境内使用 GCJ-02，境外可用 WGS84；同组路线不得混用。`poi_id` 绑定 provider、核验时间和地图来源 ID，按平台 POI、标准化地址和同名 30 米近邻去重。

### 动态快照

`planning.restaurant_snapshots[]` 使用 `restaurant-source-snapshot/v1`，遵守 `schemas/restaurant-source-snapshot.schema.json`，按餐厅、适用日期和餐窗保存：

- 分平台评分、量表、评价量、人均与查询时间。
- 营业、预约、排队、停车、菜单状态及复核时间。
- 社区查询词、样本数、发布时间、一致与冲突、推广风险和原帖引用。
- 实际操作入口、`checked_at`、`expires_at` 与来源 ID。

平台信号不能合成无来源的“综合评分”。数字取不到时使用 `status=unavailable`，记录原因、查询条件和手动入口；小红书互动数不是餐厅评分。

### 用餐方案

`planning.meal_options[]` 描述这一餐如何执行，包含餐别、时间窗、前后锚点、预算与绕行约束、统一基准路线、候选 ID、逐候选快照和路线评估、主选、备选、选择理由与切换条件。前后锚点必须记录明确名称、可定位的具体地址和坐标，不能只写“上一站”“下一站”或片区方向。

`selected_candidate_id` 必须属于候选集合，`fallback_candidate_ids[]` 至少包含一个不同实体。片区、商圈和“酒店附近”只能作为搜索锚点，不能作为候选。

餐饮层不得复制当前主选的地址、菜品、人均、营业时间或路线结论，也不得另写自由文本备选。候选事实分别以 `restaurants[]`、`restaurant_snapshots[]` 和 `meal_route_evaluations[]` 为唯一来源；切换主选时只更新结构化候选引用、排序、选择理由和 `fallback_rule`。

### 路线评估

每餐只有一条同口径直达基准，遵守 `schemas/meal-baseline-route.schema.json`。每个候选的双腿路线遵守 `schemas/meal-route-evaluation.schema.json`，并与基准使用相同起终点、交通方式、路线策略和出发时刻。

两腿门到门时间之和等于候选总时间，候选总时间减基准时间等于 `detour_minutes`。两腿端点的名称、具体地址和坐标必须严格构成“上一锚点 → 餐厅 → 下一锚点”；不得使用直线距离或估算数字替代。基准路线锚点与双腿路线端点都必须携带具体地址，供页面直接说明从哪里到哪里。保留候选不得超过数值型 `max_detour_minutes`。

## 来源与筛选

每个候选至少完成：

- 地图平台确认分店、POI、地址、坐标、电话、路线、停车和平台入口。
- 店铺官方或可靠平台确认营业、预约、菜单、人均和商家图片。
- 主选交叉至少 3 篇、备选至少 2 篇近 12 个月社区原帖，并覆盖至少 2 位作者；逐条保存原帖身份、发布时间、查询时间和来源 ID。
- 社区不可用时记录真实查询词、失败类型、手动入口和复核时间，不能用“低置信度”代替零证据。

默认排序维度可随行程调整：路线与绕行 35%，特色和偏好 20%，平台口碑 15%，社区共识 10%，营业排队预约和停车 15%，来源完整度 5%。综合分只用于系统内部选择，不向旅行者展示分数、加分拆解、长篇选择理由或切换规则；页面突出综合推荐，并将结构化备选作为可横向滚动、默认展开且可收起的完整餐厅卡。赶车、高海拔、长途驾驶或晚到时提高路线与出餐权重。

### 路线前美食主题加分

路线确认前的 `route-context.json` 可以提供“这座城市值得吃什么”的先验，但不能直接证明具体门店质量。餐厅排序按以下边界使用：

1. 只有某一菜品或美食类别在至少 2 位独立作者的近期原帖中重复出现，且已记录原帖引用、查询时间、冲突和推广风险，才形成可评分的 `food_theme`。
2. 某候选只有在店铺官方菜单、可靠平台菜单或已核验特色菜字段能够证明实际提供该主题菜品时，才获得“地方美食主题吻合”加分；店名、菜系标签或单篇笔记提及不能单独触发。
3. 该加分最多占总分 3 分，并包含在原有 10 分“社区共识”权重内；剩余社区分继续评价该具体门店的近期口味、份量、排队、服务和推广风险，总分仍为 100。
4. 同一原帖同时支持目的地美食主题和具体门店评价时，只计入更具体的门店维度，不能重复加分。路线、营业、预算或饮食限制不合格的候选不能靠主题吻合翻转为主选。
5. 小红书不可用、主题证据不足或所有合格候选都不吻合时，主题加分统一为 0，并明确“未使用该加分”，不得臆造地方特色或惩罚缺少社区覆盖的候选。

### 高德候选与自由选择

中国境内没有可用的大众点评、美团授权来源时，高德是餐厅候选的基础来源，不是“无餐厅数据”的降级提示：

1. 用上一站出口、酒店或下一站入口的已核验 GCJ-02 坐标调用高德周边搜索，关键词按餐别、菜系和用户限制组合，半径服从餐窗与最大绕行约束。
2. 周边结果只用于发现。对保留候选逐个用 POI ID 查询详情，核准精确分店、地址、坐标、营业、人均和高德展示评分，再计算前后两腿路线。
3. 高德返回顺序称为“高德搜索结果”或“高德综合排序候选”，不得声称“高德官方推荐”。最终系统推荐仍按本 Skill 的路线、营业、偏好、平台信号、社区证据和来源完整度综合生成。
4. 高德返回评分但未返回评价量时，保留并展示评分，同时明确“评价量未取得”；不得改写成整个平台评分未取得，也不得据此声称口碑最佳。
5. 已核验 `poi_provider=amap` 与 `poi_id` 时，生成 `https://uri.amap.com/poidetail` 门店详情入口；有 GCJ-02 坐标时同时生成 `https://uri.amap.com/navigation` 到店入口。URI 参数来自已核验 POI 和坐标，不猜测商家购买、预约或团购深链。

页面突出显示 `selected_candidate_id` 对应的综合推荐，并在其下以横向滚动列表显示 `fallback_candidate_ids` 对应的备选完整卡；每张备选卡默认展开且可收起，保持稳定卡宽，不因候选数量变多而压缩。不提供“路线最优、高德评分、附近可选”排序，也不提供“选择这家”或“已选为本餐”状态。切换条件仍保留在结构化 JSON 中供系统复核，不向旅行者展示长篇规则。每张餐厅卡的前后两段路线以“起点名称 → 终点名称”标题直接链接高德路线，不在操作按钮区重复输出同名路线按钮。每餐提供一个以上一行程锚点为中心的“在高德查看附近餐厅”入口；每张餐厅卡最多提供一个规范化的“在高德查看门店”入口，不再另列“导航到店”，来源中的高德门店别名链接和餐饮事件级链接也不重复输出。主推荐的“查看门店”和“附近餐厅”统一放在推荐卡底部，形成当前推荐与寻找替代的同层操作区。

推荐门店存在满足门店身份与时效要求的小红书原帖时，页面直接展示原帖标题、作者和链接。没有门店级原帖时，不得把城市级美食主题笔记冒充门店推荐；只展示“在小红书搜索这家门店”的搜索入口，不展示内部主题加分，也不写成门店口碑结论。页面中的平台名称统一使用“高德”和“小红书”，不得暴露 `amap`、`xiaohongshu` 等内部标识。

## 图片与链接

每个候选至少提供一种可视证据：

- 可展示图片来自用户、商家官方明确允许素材或开放许可图片，并记录 `alt`、作者或机构、许可、原始页面和查询时间。
- 无合法图片时使用 `kind=link_preview` 的官方相册、地图详情或社区原帖卡，不复制、下载或热链临时 CDN 图片。

不得使用无来源菜品图、截图、渐变色块或通用美食图冒充餐厅实景。

## 共享状态

将其他 Agent、排程或页面需要读取的餐厅身份、地址、坐标、POI、菜系和特色菜写入 `shared_entities[]`，动态评分、人均、营业、排队、预约和路线距离保留在本次任务实体与快照中。所有内容都只属于当前 workspace，不跨行程缓存。

## 完成门槛

一顿正餐进入 `confirmed_planning` 前必须满足：

- 有 2～3 个去重的实体候选，或有来源支持的受限声明。
- 每个候选有可定位 POI、特色菜、动态营业状态、平台入口和合法可视证据。
- 中国境内高德 POI 候选有可打开的高德门店详情入口；有坐标时同时有到店导航入口。
- 每个候选有统一基准下的双腿路线和额外绕行。
- 平台评分与社区信号分开并带查询时间；动态价格、营业、排队和预约有复核时间。
- 主选、至少一个备选和自动切换条件明确。

“同商圈”“酒店附近”或“到时再看”不能通过门槛，只能作为带查询入口和应急补给的最后降级。
