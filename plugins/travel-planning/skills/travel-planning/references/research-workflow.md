# 景点与路线研究

在生成逐日行程前完成本流程。研究结果必须写入 `itinerary.json` 的 `planning`，日程事件则引用对应的景点和路线编号。

路线确认后还要执行[行前就绪检查](trip-readiness.md)。景点与交通研究解决“去哪里、怎么串”，行前就绪检查解决“能否入境、如何携带行李、何时预订、发生变化时如何复核”。

## 1. 建立景点候选表

每个候选景点至少记录：

- 景点名称、区域、坐标或可定位地址。
- 当季看点和近期体验；标注适用月份及信息查询日期。
- 最佳时段：清晨、白天、日落、夜晚或均可。
- 时段理由：采光、夜景、演出、温度、客流、开放时间或交通限制。
- 入口到出口的核心玩法与细粒度时间轴。每个 checkpoint 记录开始/结束时间、节点类型、名称、是否必达和具体动作；相关时补现场看点/讲解、图片、内部交通、从上一点的移动方式、费用引用、餐饮引用、操作链接和失败备选。
- 免费项目和付费项目；付费项目必须拆成基础门票、景区内必选交通、可选体验和互斥套票，记录单价、计价单位、人数/数量、全体小计、是否计入基线、预约方式、截止时间、价格状态和来源。
- 建议游览时长、体力等级、天气限制和人群限制。
- 推荐入口、入口选择理由、建议出口，以及入口的可定位名称。
- 官方事实来源与社区体验来源分别记录。
- 景点运营信息按旅行日期分别记录：开放、停止售票、停止入场、闭园、节假日覆盖、临时公告和查询时间；禁止继续塞进单一 `opening_status` 字符串。
- 预约/抢票任务绑定目标景点和计划事件：记录目标参观日期/场次、人数、票种、官方放票规则、`sales_open_at`（取得时）、下次操作时间、截止、无票备选和官方预约入口。实体地址、官网、预约入口和公告入口分别记录；未知放票时间不能写成“提前抢票”，应写明下一次何时去哪里复核。
- 为每个景点地点和日期建立结构化天气对象：固定图标代码、气温、降水、风、紫外线、日出日落、预警、状态、查询/复核时间和用户可打开的天气网站。天气 API 文档页不能充当天气查看入口。
- 节点图片只使用用户素材、官方允许素材或明确开放许可图片，记录 `alt`、作者/机构、许可、原始页面和查询时间。小红书图片不复制，改为近期体验链接卡。

小红书用于体验层判断时，优先查看与旅行月份一致或最近 12 个月内的内容，并交叉验证至少 3 条近期笔记；若只能找到较旧内容，降低可信度并标注。研究偏远景点交通时，组合检索“目的地＋月份＋包车/司导＋换乘/路况/行李/避坑”，用来发现表定班次之外的真实门到门成本和风险，再回到平台、承运公司或司机服务合同核对。

## 2. 形成交通边

对以下连接分别研究，不要只研究景点本身：

- 出发城市 → 目的地城市。
- 机场/火车站/客运站 → 酒店或首个景点。
- 酒店 → 每天首个景点入口。
- 相邻景点的“出口 → 下一景点入口”。
- 每天最后一个景点 → 酒店。
- 目的地城市 → 返程站点或下一城市。

每条交通边至少比较适用的两种方式，并记录：

- 方式：步行、公交、地铁、打车、火车/高铁、飞机、轮渡、景区接驳、长途大巴或包车＋司机/司导。
- 精确起点和终点，尤其是景点入口、车站和航站楼。
- 线路/车次/班次、换乘站、发车区间、预计等待和步行距离。
- 车上时间、门到门时间、费用、购票渠道和退改限制。
- 首末班或停止入场时间造成的约束。
- 推荐方式、选择理由和一个可执行的备选方式。
- 信息来源、查询时间和实时性状态。

火车/高铁优先用 12306 核对；长途大巴可先用携程查询，再尽量用客运站或承运方确认。实时余票、动态价格和临时班次只能记录查询时状态，不得承诺未来仍可购买。

以下情况至少比较一个包车＋司机/司导方案：

- 铁路、航班或大巴需多次换乘，或首末班无法衔接。
- 起终点距车站/机场较远，公共交通的门到门时间明显高于包车。
- 携带较多行李、有老人儿童、夜间抵达，或多人分摊后价差可接受。
- 需要一天串联多个偏远景点，而景区接驳频率低或停运风险高。

包车方案除通用交通字段外，还必须记录：车型与座位/行李容量、按车还是按人计价、司机服务时长、超时费、油费/路桥/停车是否包含、异地返程或司机住宿费、上下车点、取消退改、服务商与车辆/司机资质、保险与应急联系方式。不根据小红书单篇笔记、私人聊天或无合同报价确认资质与安全性。

## 3. 计算串联顺序

先按地理位置将景点聚成同日片区，再用以下约束排序：

1. 强时段景点优先占用对应窗口，例如日出、日落、夜景、定时演出。
2. 有停止入场时间、预约时段或末班交通的节点优先锁定。
3. 选择同方向移动的路线，避免折返；比较的单位是门到门时间，不是直线距离。
4. 步行超过用户承受范围、携带行李、深夜或天气不佳时，切换为公交、地铁或打车。
5. 每半天保留缓冲；跨城交通按风险增加 30–120 分钟缓冲。
6. 如果一个景点会显著破坏路线或挤占核心体验，将其放入未采用清单，并写明原因。

## 4. 研究并插入餐饮事件

餐饮不是行程末尾的推荐清单，而是和景点、交通同级的时间轴事件。完整方法见[餐厅候选研究与路线适配](restaurant-research.md)：

- 先根据景点结束时间、下一段交通和真实片区建立用餐时段，再研究具体餐厅；片区只能作为搜索锚点，不能当餐厅候选。
- 正常正餐至少比较 2 个、优先 3 个候选。每个候选记录分平台评分/评价量、近期社区共识、特色菜、人均、营业、排队/预约、图片/相册来源和查询时间。
- 对每个候选计算上一事件出口到餐厅、餐厅到下一事件入口的门到门路线和额外绕行；主选与备选必须来自同口径比较。
- 长途驾驶、高海拔、赶车和晚到日优先保证热食、补水和准时，不为网红店增加折返。
- 当天行程跨过 11:30–13:30 或 17:30–20:00 且不在交通工具内完成用餐时，必须创建相应 `meal` 事件。
- 景区内小吃、补水和茶歇可作为 checkpoint 并引用 `meal_id`；若承担午餐或晚餐，同时生成顶级 `meal` 事件并用 `parent_attraction_event_id`、`checkpoint_id` 关联，费用只计一次。
- 禁止把“途中午餐”“入住后就近晚餐”只写进交通、住宿或休息事件的 `details`。

## 5. 质量检查

- 每个进入日程的景点都有 `attraction_id`，并能回溯到景点研究记录。
- 每个景点事件都有稳定事件 ID、结构化 `admission`、入口/出口、至少一个必达 checkpoint 和按时间可执行的内部顺序。
- 每个 checkpoint 有 `time`、`end_time`、`kind`、动作和连续顺序；图片、讲解、内部交通、餐饮、费用和链接均附着到实际发生的节点。
- 每个景点事件通过 `weather_id` 引用结构化天气对象；对象有固定图标代码和天气网站，只有改变动作的影响进入 checkpoint 条件或备选。
- 需要预约的景点有绑定该事件的 booking task，页面能直接显示何时操作、抢什么、几人、截止和失败备选。
- 相邻两个非休息事件之间都有明确的交通事件或可解释的步行衔接。
- 所有交通事件都写清起点、终点、交通方式和门到门耗时。
- 每个付费项目都能区分景区基础票与二次消费。
- 每个景点事件都有 `cost_items[]`，且至少有一项 `kind=base_ticket`；免费景点也要显式记录0元。
- 套票、单票和内部项目标明 `pricing_role`，互斥方案不得重复计入基线。
- 无法取得公开价格时，费用项写明未取得的来源层级、最后查询时间、查询条件和手动入口，不允许只有“待确认”。
- 页面中的预算由事件费用派生；景点详情、交通、天气和费用必须能在对应的逐日事件中直接读到。
- 每个跨越正餐窗口的完整旅行日都有 `meal_id` 绑定的餐饮事件，能直接回答何时、主选/备选是谁、谁推荐、特色是什么、前后多远、额外绕行多少、何时切换。
- 每个移动日都有退房到入住之间的大件行李方案；跨时区或红眼航班已与酒店入住夜对齐。
- 每个“适合晚上”的景点都已核对夜间开放和返程方式。
- 节假日、地方活动、每周闭馆和季节停运均已与具体日期交叉检查。
- 国际行程已检查入境/过境、分开出票、保险、紧急联络、货币支付和通信；不适用项已明确标记。
- 采用包车＋司机/司导时，有一个可执行的备选承运方或公共交通方案，并已说明报价包含项、资质核验状态和取消条件。
- 页面与 JSON 中不存在未经标注的实时价格、余票或班次推断。
