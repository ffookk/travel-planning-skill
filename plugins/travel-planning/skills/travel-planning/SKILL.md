# 旅行规划

将旅行需求转化为可执行的行程，并生成一个采用移动端时间轴结构、可独立打开的 HTML 页面。

## 两阶段门槛

1. **路线建议阶段**：根据出发地、目的地区域或指定路线、日期/天数、人数、预算和偏好，给出 2～3 个路线方案。每个方案展示城市顺序、停留天数、主要交通、大致预算、节奏、亮点和风险。
2. **用户确认阶段**：让用户选择、合并或调整路线。除非用户明确说“直接按你推荐的做”，否则不得跳过确认门槛进入大规模深度调研。
3. **深度规划阶段**：路线确认后，再并行研究景点、城际交通、住宿、餐饮、天气和风险，并合成为逐日行程。

路线建议阶段不虚构精确车次、实时余票或酒店库存，只提供足以做路线决策的区间信息。

## 工作流程

1. 只收集会显著影响方案的信息：目的地、日期或天数、出发地、出行人数、行程节奏、预算、兴趣、住宿位置和硬性限制。信息不足时，在不涉及日期、目的地或无障碍安全风险的前提下，说明合理假设并继续规划。
2. 按[标准规划流水线](references/planning-pipeline.md)执行“公共库复用 → 建档与路线确认 → 前置采集 → 主 Agent 编排 → 独立审查 → 稳定候选晋升 → 渲染交付”。开始新行程时先按[跨行程公共资料库](references/shared-travel-library.md)搜索并把选中的实体 revision 固化到本次 `library-seed.json`；再检索历史 workspace 作为线索。公共库只提供稳定基线，日期、价格、开放、库存、天气和临时公告必须重新查询。在排日程前完成[景点与路线研究](references/research-workflow.md)；路线骨架、景点出入口与住宿锚点稳定后，按[餐厅候选研究与路线适配](references/restaurant-research.md)完成逐餐候选、动态快照和双向路线比较。查询不同平台时遵循[信息获取与核验策略](references/source-strategy.md)。复杂行程或需要子 Agent 时，按[行程研究工作区](references/research-workspace.md)创建本次独立目录，通过文件共享任务、来源和结果。
3. 路线确认后，先运行 `python3 skills/travel-planning/scripts/research_sources.py preflight --city "<首个目的地>"`，并根据本次路线把必需来源逐个追加为 `--require <source>`。预检必须真实完成 MCP `initialize`、`tools/list` 和只读上游 smoke query，同时检查天气接口及小红书安装/登录态；不能用 `capabilities` 的静态结果代替。必需来源失败时先采用[实时数据工具](references/live-data-tools.md)中的合规 fallback 或修复运行环境，不得直接启动依赖该来源的研究任务。需要航班、火车、酒店、天气、地图、小红书体验研究或手动复核链接时，按[实时数据工具](references/live-data-tools.md)查询。环境中已配置的飞猪、飞常准和高德等只读查询属于深度规划的正常步骤，直接执行，不逐次请求用户同意，也不因预计调用次数或额度提示而暂停；这项默认仅覆盖查询，绝不扩大到下单、占座、付款、发送消息或修改订单。飞猪通用发现调用插件内 `$flyai`，中国境内地点与路线调用 `$amap-maps`，航班运行、价格、火车及空铁联运调用 `$variflight`，小红书体验研究调用 `$xiaohongshu`。需要写入研究 workspace 的飞猪和飞常准候选使用本 Skill 的标准快照适配器，并同时传入本次 `--workspace` 和已分配的 `--task-id`，让 `travel-source-snapshot/v1` 直接落到 `snapshots/<task_id>/`。研究结果只提交 `source_snapshot_ids[]`，交通或住宿候选再通过 `inventory_refs[]` 精确绑定 `snapshot_id + offer_id`；不得让供应商原始字段进入行程层。小红书旅行研究默认只读，并遵循[小红书集成](references/xiaohongshu-integration.md)，不得把 Cookie、二维码或临时令牌写入行程 workspace。
4. 根据行程条件执行[行前就绪检查](references/trip-readiness.md)。境外或跨境行程必须覆盖入境/过境、官方安全与健康提示、保险、货币支付、通信和时区；所有行程都要检查节假日/活动/闭馆、行李衔接、特殊人群约束、紧急信息和分阶段复核。无关项目显式标记 `not_applicable`，不要用空白代替判断。
5. 对每个候选景点确认：当季是否值得去、适合白天/日落/夜晚的哪个时段、核心玩法、普通游览时长、免费与付费项目、适用日期的开放/停止售票/停止入场/闭园、预约方式与官方入口、推荐入口/出口、从住宿点或上一站如何到达该入口，以及从入口到出口的必达卡点、内部顺序、各点时间、动作、讲解、内部交通、可用图片、途中补给和最晚离开时间。
6. 再研究城市间与景点间的交通边：步行、公交、地铁、打车、火车/高铁、飞机、轮渡、景区接驳、长途大巴以及包车＋司机/司导。开放式航班和铁路候选发现必须使用覆盖查询，同时取得最早出发、最晚出发、时长优先、价格优先和平台推荐结果，合并去重后再筛选；不得用单次低价榜推断全天无合适班次。火车或飞机换乘复杂、景点偏远、携带行李、有老人儿童或多人分摊成本时，必须将包车方案纳入门到门比较。记录班次或服务时间、起终点、换乘、耗时、费用、步行距离、末班限制、可信来源和备选方案。航班还要记录行李额度/费用、是否分开出票、是否需要自行提取并重新托运，以及出发到达的当地日期和时区。
7. 先按地理位置聚类，再根据昼夜适配、开放时间和交通方向排序。计算门到门时间，不得只记录车上时间；跨城移动必须加入进出站、安检、候车、取行李和市区接驳缓冲。退房到入住之间必须写明行李寄存、转运或随车方案。先用这些硬时间生成可行性窗口，再比较价格；价格更低但破坏当日核心行程的候选不得作为默认主选。
8. 对营业时间、临时关闭、门票规则、公共交通时刻、天气、签证规则和价格等时效信息，使用实时、权威来源核验。区分已核验事实、平台信息、用户经验和估算，并记录 `checked_at` 与来源网址。
9. 前置采集全部提交后，由主 Agent 按稳定 ID 汇总并按照[行程数据结构](references/itinerary-schema.md)创建 `itinerary.json`。先生成只含硬时间、门到门交通、餐窗和最晚离开的候选事件流，立即运行一次可行性审查；任何景点/用餐重叠、接驳缓冲不足、晚餐/夜景晚于末班车或住宿入住衔接失败，都必须在补餐厅细节和渲染前重排。无法同时满足时自动生成“换交通方式、缩短景点、取消次要活动”的降级顺序，不能把冲突留成一句提醒。`planning` 保存可追溯的规范化研究记录；`days[].events[]` 必须把实际执行所需的景点、交通、正餐、天气、预约和费用信息合并到对应事件，不能要求读者回到页面上方的研究区拼接信息。发现缺口时创建独立修补任务，不能在写页面时临时猜补。
10. 在渲染前执行“事件流完整性门槛”：
   - 每个事件都有稳定 `id`。每个景点事件写明当日结构化 `admission`、入口和出口、`execution.checkpoints[]` 内部时间轴、最晚离开、`weather_id` 和 `cost_items[]`。
   - `admission` 必须区分开放时间、停止入场、预约方式、核验/入园要求和临时公告；官方主页、预约入口、公告入口和实体地址不能混成一个“官网地址”。
   - 每个 checkpoint 至少写明时间段、节点类型、是否必达和具体动作；适用时补现场看点/讲解、节点图片、内部交通、费用、天气条件、链接、途中补给和失败备选。
   - 需要预约或抢票的景点通过 `booking_task_ids[]` 绑定预约任务；在景点卡内直接展示抢什么、几人、放票规则、何时操作、截止时间、主备方案和官方操作入口。
   - `cost_items[]` 至少区分基础门票、景区内必选交通和可选体验；写明单价、数量、2人/全体小计、是否计入基线、时效状态及来源。套票与单项价格不能重复相加。
   - 每个交通事件通过 `route_id` 合并出口到入口、线路、门到门时间、费用、推荐理由、备选和实时状态。使用飞猪或飞常准候选时，交通/住宿对象必须通过 `inventory_refs[]` 绑定具体快照和 offer；中国铁路候选另带 12306 复核状态与入口。
   - 每个住宿候选必须保存本次成人数、房间数、床型、连续入住夜和同一酒店要求。商圈搜索只能用于发现候选，采用前必须用酒店全名及地图坐标核对城市、行政区、实体地址和目标锚点；跨区或身份不一致的结果直接淘汰。供应商没有返回剩余房量，或没有按多间同房型校验时，只能标为“报价候选/下单前复核”，不得写成“有房”或“可订”。
   - 每个完整旅行日的午餐和晚餐按实际时间窗写成 `meal` 事件。正常正餐必须有 2～3 个经平台 POI、地址和近邻规则去重的可定位餐厅候选；POI 必须绑定实际地图查询来源。分平台保存评分/评价量、近期社区共识、特色菜、人均、营业、图片/相册来源，并基于每餐唯一的直达基准计算“上一事件 → 餐厅 → 下一事件”和额外绕行；明确主选、至少一个结构化备选和切换条件。受限场景少于两个候选时必须有来源支持的例外与随身餐/便利店方案。禁止用“步行圈”“途中午餐”“到店再看”通过门槛。
   - 天气保存为可引用对象，包含固定 `icon_code`、摘要、温度、状态、查询时间和可供用户打开的天气网站。景点卡右上角只显示可点击天气图标；会改变动作的风雨或预警写入受影响 checkpoint 的条件/备选，不再单列“天气影响”事实行。
   - 总预算从事件费用派生。允许在数据中保留聚合结果，但页面不能另设一套与事件明细脱节的手工预算。
   - 未获得价格时，记录“未从官方公开页取得”，附查询时间、待核字段和可执行查询入口；不得用裸的“待确认”通过门槛。
11. 另起审查步骤检查字段引用、时间空间冲突、正餐窗口、来源层级和页面可执行性。确定性审查至少运行两次：候选事件流完成后先审硬时间和交通可行性，动态候选绑定完成后再做最终审查；随后由独立审查 Agent检查事实冲突和语义可执行性。审查结果写入 workspace，只有阻断项清零后才能生成页面：

   ```bash
   python3 skills/travel-planning/scripts/audit_itinerary.py itinerary.json --output state/audit.json
   python3 skills/travel-planning/scripts/render_itinerary.py itinerary.json itinerary.html
   ```

12. 打开或渲染 `itinerary.html`，分别检查手机和桌面宽度。交付前修复内容溢出、图片失效、信息过密和时间轴错位。
13. 同时交付 `itinerary.html` 与 `itinerary.json`，并总结主要假设、路线选择理由、需要立即预订的项目及出发前需要重新确认的信息。

## 动态子 Agent

协作能力可用且任务存在两个以上相互独立的研究域时，深度规划必须使用子 Agent 并行调研。多城市、超过 3 天、候选景点超过 8 个，或同时涉及铁路/航班/大巴/包车，均视为明确触发条件；不能只在文字中说“并行研究”却由主 Agent 串行完成。只有协作槽位不可用、用户明确禁止委派、任务仍处于路线建议阶段，或任务之间存在硬依赖无法并行时才可不拆分，并在交付中说明原因。

并行前先按[子 Agent 编排](references/agent-orchestration.md)和[行程研究工作区](references/research-workspace.md)创建任务。优先使用 `attractions`、`route-data`、`stay-food`、`restaurant-research`、`weather-risk` 五个可扩展任务域；`stay-food` 负责住宿与餐窗初稿。餐厅链路必须拆成带显式 stage、不可覆盖的 `restaurant-discovery` → `route-data-meals` → `restaurant-ranking` 三个任务；前者输出餐厅/快照/候选集，中间任务输出每餐唯一基准和候选路线，末项只输出最终排序。后两项只能在依赖结果完整提交后创建；依赖文件纳入 `input_revision`，三阶段候选集合必须完全一致，空 `complete` 会被拒绝。每个 assignment 都携带只读公共库 seed 和领域结果模板。子 Agent 只提交自己的 `results/<task_id>.json`、`sources/<task_id>.jsonl`、`snapshots/<task_id>/` 和 `evidence/<task_id>/`；结果只允许包含规范化 `entities`、`source_snapshot_ids`、`catalog_candidates`、`event_bindings`、`constraints`、`unresolved` 和短摘要，不得直接写公共库，不得提交独立行程或调研汇报，也不得共同编辑 `itinerary.json`、HTML、Skill 或渲染器。

主 Agent 始终负责：确认用户目标、确定路线版本、分配不重叠任务、合并结果、解决来源冲突、执行最终可行性检查以及生成页面。子 Agent 的结果是研究输入，不能绕过主 Agent 的验证直接写入最终日程。

## 信息源规则

- 景区官网、文旅部门、交通运营方和铁路/客运官方渠道用于确认开放时间、门票、入口、运营时间和规则。
- 小红书等内容社区用于判断当季体验、拍摄时段、拥挤程度、实际玩法、餐厅口味/份量/排队/服务体感、包车真实耗时、道路与行李体验以及容易踩坑的位置；正常正餐主选至少交叉查看 3 条近期原帖，备选至少 2 条。来源客观不可用时必须记录不可用状态、原因和手动查询入口，不得伪造共识。社区互动数不是餐厅评分，单篇笔记不能证明营业、价格、资质或安全性。
- 12306 用于核对中国铁路车次、出发到达站、日期、时刻和席别价格；无法访问实时结果时明确标注“待在 12306 复核”，不得虚构余票。
- 携程等平台可用于查询长途大巴、接驳、包车＋司机/司导、航班和辅助比价；班次、资质、报价包含项和退改最终尽量回到承运方或客运站核验。无法核验时保留平台来源和查询时间。
- 优先使用环境中已配置的官方 API、MCP 或平台公开查询页。必要时可在 GitHub 调研备选工具，但必须先核对上游授权、许可证、维护状态、数据范围和安全边界；不得默认安装或执行逆向私有接口、轮换 UA/IP 或规避风控的项目。
- 本插件复用的通用能力包括 `autoclaw-cc/xiaohongshu-skills`、飞猪 FlyAI、飞常准 Aviation/Tripmatch MCP、Open-Meteo、高德官方 MCP/Web 服务和 Nominatim/OpenStreetMap。供应商级 `$amap-maps` 与 `$variflight` Skill 负责引导 MCP，主 Skill 负责跨来源编排。CLI、MCP 与 API 可以并存，不为形式统一重复实现成熟能力。动态交通与住宿来源统一转换为 `travel-source-snapshot/v1`；12306 仍作为中国铁路最终复核渠道，携程和景区官网在没有获授权实时 API 时采用官方/平台查询页的用户会话交接。`capabilities` 中的 `adapter_available` 不等于实时健康；深度规划以本次 `preflight` 结果为准。
- 对已在本 Skill 中配置并列明数据边界的只读查询，直接发送完成查询所必需的日期、城市、车站、机场、住宿区域和人数条件，不逐次征求用户同意，也不以调用额度为规划阻断。新增未评估供应商、安装新工具、配置新付费凭证或任何写操作仍须单独评估；默认优先官方、低风险、只读接口。
- 公共搜索优先；只有成功搜索仍缺少必要信息，或页面必须交互、登录后才能查看时，才使用浏览器操作。不得绕过登录、验证码或访问限制。
- 自动查询失败或无合规工具时，不能只写“待查询”；必须提供用户可手动查询的官方或平台 HTTPS 入口、需输入的日期/地点/车站等条件、待复核字段和建议复核时间。具体规则见[信息获取与核验策略](references/source-strategy.md)。
- 来源冲突时，以官方且更新较新的信息为准，并在数据中记录冲突与取舍。

## 交互与操作边界

- 页面交互规范见[交互页面规范](references/interactive-page.md)。地图、官网、购票、酒店、餐厅和交通平台可作为普通 HTTPS 跳转链接。
- “购票”“预订”“购买”按钮表示跳转到外部平台，不代表已完成购买；按钮旁展示平台名称、查询时间和价格实时性提示。
- 未经用户对具体项目、日期、数量、价格和乘客/入住人确认，不得代替用户提交订单、付款、发送消息或修改预订。
- 外部链接必须来自实际查询结果或官方固定入口，不得拼接、猜测深链。无法得到稳定详情链接时使用平台搜索页，并明确搜索关键词。

## 页面要求

- 使用吸顶黄色页头，展示行程标题、摘要和日期标签。
- 左侧为时间轴，右侧为行程卡片；沿用参考图的信息层级，但不复制其品牌元素。
- 支持景点、交通、餐饮、住宿、休息和提示六类事件。
- 页面以逐日事件流为唯一主视图；不在事件流之前重复渲染景点研究卡、景点间交通表、天气表或独立预算表。
- 景点卡必须包含图片组（有可靠图片时）、时长、区域、开放/停止入场、基础门票、景区内必选交通、可选体验、基线小计、预约方式、推荐入口、内部时间轴、导航和购票链接。
- 景点卡右上角使用带无障碍名称的天气图标，点击打开对应地点和日期的天气网站；页面正文不再重复一行“天气影响”。无有效天气入口时不显示假图标。
- 景点卡将“景区内怎么玩”作为默认展开的嵌套时间轴；每个节点显示时间、名称、是否必达和动作，适用时显示讲解、图片、移动方式、内部交通、途中餐饮、操作链接和失败备选。预约/抢票动作紧邻“开放与预约”，不放在远离事件的汇总报告里。
- 餐饮卡必须展示主选和 1～2 个备选；每个候选回答谁推荐、平台评分与评价量、近期社区共识、图片/相册来源、特色菜、人均、营业、排队/预约、停车、从上一站和去下一站的距离时间、额外绕行、操作链接和切换条件。不得把不同平台评分揉成一个无来源分数，不因追逐热门餐厅制造明显折返。
- 交通卡必须包含准确起终点、交通方式、具体线路、门到门时间、费用、推荐理由、备选、行李方案和实时状态。中国境内的本地/驾车段还必须保存高德 `map_route` 起终点坐标。内嵌路线按宿主设备切换：桌面使用无需 Key 的 `ditu.amap.com/dir`，移动端驾车使用 `m.amap.com/navigation/carmap`；不得把 iframe 宽度或 `meta viewport` 当作移动 UA。地图默认使用紧凑预览，并提供宿主页“全屏查看/退出全屏”按钮；不支持全屏时打开当前高德路线。始终保留独立 HTTPS 路线链接，首次登录提示可由用户关闭，iframe 加载失败时不得只剩文字。
- 页面提供日期跳转、方案切换、地图导航、来源查看，以及外部购票/订房/餐厅/车票入口。执行所需的详情默认展开；只能把长来源说明等次要内容折叠，开放时间、入口、路线、天气、门票和费用不得藏在折叠区。
- 待预约、费用、天气、行李、每天强度和备选方案优先附着到相关日期/事件；顶部只保留路线假设和必须立即处理的少量总控提示，不能复制完整明细。
- 使用响应式布局：优先适配窄屏手机，在桌面端居中舒适展示。
- 使用无障碍语义化 HTML，提供清晰的键盘焦点、替代文本、足够的颜色对比度，并兼容减少动态效果设置。
- 支持打印模式，隐藏交互控件，并尽可能避免行程卡片跨页断开。
- 不得虚构预订结果、实时精确价格、开放时间或库存。所有估算必须明确标注。
- 未获得用户另行明确授权时，不得预订、购买、发送消息或修改已有订单。

## 图片与地图

优先使用用户提供的图片；否则使用景区官方明确允许展示的素材或带清晰开放许可的图库图片。图片既可属于景点卡，也可绑定某个 checkpoint；均需记录替代文本、作者/机构、许可、原始页面和查询时间。小红书搜索结果用于生成带标题、作者、互动数和原帖链接的“近期体验参考”卡；不得把临时 CDN 封面、未授权笔记图片或详情页截图热链/复制为景点主图或节点图。没有合适图片时省略，不生成假图片、色块或图钉占位。地图链接应使用普通 HTTPS 地址。

## 质量标准

最终结果优先回答行动问题：几点到、从哪个门进、必须到哪些点、按什么顺序走、最晚几点离开、何时抢什么票、两人花多少、下一段怎么走、何时在哪里吃什么，以及失败时改什么。删除目的地百科、重复的安排理由、泛化提醒和研究过程；一段文字如果不会改变旅行者的时间、地点、动作、费用或备选，就不放进事件卡。优先保证可执行性，而不是追求行程数量或汇报完整感。
